# Yihop｜給門市使用的備貨與叫貨工作台

門市每天都要判斷要叫多少貨。除了架上還有多少，還得想明天廠商有沒有送、到貨後要撐幾天、碰上低溫或農曆特殊日期會不會需要多備一點。

我最初做 Yihop，就是不想讓這些資訊一直散在試算表和人的記憶裡。它把門市盤點、建議叫貨、廠商公休、天氣和歷史紀錄整理進同一個操作畫面；人員最後仍能依現場情況調整叫貨數量。

**[其他作品與面試導覽](https://github.com/garyai8146-jpg/Yihop_LineBOT/blob/main/PORTFOLIO.md)**

## 現在可以做什麼

- 選擇**潮州店**或**內埔店**、盤點人員、日期與廠商，逐項填寫庫存。
- 依基礎安全庫存、每箱數量、週末及農曆初一／十五規則推算建議叫貨量。
- 判斷供應商公休日：若預計到貨日休息，順延到下一個可到貨日並標示提醒。
- 讀取中央氣象署今明 36 小時預報，**只使用預計到貨日確實涵蓋的時段**；超出預報範圍不套用臆測的天氣加成。
- 將盤點與叫貨紀錄寫入 Google Sheets，成功後產生可複製到 LINE 的叫貨文字。
- 管理端查看歷史、依門市篩選，以及比較系統建議與實際訂購數量。

## 這次把早期容易出錯的地方補上了

最重要的是**送單不能只要有一份寫入就說成功**。以前會分別寫進「叫貨紀錄」和「紀錄_廠商」，任何一份失敗都有可能留下不一致。

現在每次送單會產生唯一編號，先檢查主紀錄，再核對廠商紀錄。若其中一頁沒成功，畫面會顯示錯誤並保留原本的編號與內容，允許補送；重試時會先檢查同編號是否已經完整寫入，避免簡單的重複追加。

這是 Google Sheets 上的**可驗證、可重試設計**，不是跨工作表的真正資料庫交易：不同使用者同時從不同工作階段送同一單、網路不穩等情況，仍可能需要人工核對。

另外也修正：

- 同名品項在不同廠商／分類的輸入欄位互相影響。
- 目錄順序變更時，同品項的識別碼不再跟著列號變動；若同分類裡有同名重複品項，會停止送單並提醒先整理目錄。
- 庫存／箱數為無效數字或箱數為零時，拒絕不安全計算。
- LINE 數量保留小數，例如 1.5 箱不會被直接截成 1 箱；也不再把訂單文字拼進自訂 JavaScript。
- 管理分析只對登入的管理者顯示；門市人員使用一般盤點畫面。

## 第一次啟動前：先設定帳號與憑證

**這版新增必要的安全設定。沒設定兩組 PIN，網頁會停止在安全設定提示，不會開放訂單資料。**

1. 安裝 Python 套件：`python -m pip install -r requirements.txt`
2. 將 `.streamlit/secrets.toml.example` 複製成 **不提交至 Git** 的 `.streamlit/secrets.toml`，填入原有中央氣象署金鑰及 Google Sheets 服務帳戶資訊。正式部署時請用 Streamlit 平台的 Secrets。
3. 另外設定 **`YIHOP_STAFF_PIN`** 和 **`YIHOP_ADMIN_PIN`**，兩者須不同，各至少 12 個字元且不可太容易猜。可各執行一次 `python -c "import secrets; print(secrets.token_urlsafe(24))"` 產生隨機值。
4. 確認 Google Sheet 服務帳戶有對應試算表的**編輯權限**，並在第一次使用前備份工作表。
5. 執行 `streamlit run Yihop.py`，分別測試門市及管理者登入。

程式讀取環境變數或 Streamlit Secrets 中的 PIN；**不要直接在 Python 程式碼或 README 寫入真實密碼**。目前採共享 PIN 的應用層保護；若開放到外部網路，建議另加身分驗證閘道、個人帳號、伺服器端登入限流與操作稽核，不應把它當成完整企業級權限系統。

### 既有 Google Sheet 會變嗎？

第一次成功送單時，會沿用原本欄名，**在需要時補上**「分類」「品項鍵」「送單編號」「送單時間」四個欄位。舊的歷史資料不會被自動刪除；新資料會帶著唯一送單編號，便於查核。

目前仍沿用「叫貨紀錄」和「紀錄_廠商名稱」的結構。不要在未備份資料的情況下直接修改或刪除這些工作表。

### 本機回歸測試

不需要 Google 金鑰即可驗證主要計算與送單流程：

```powershell
python -m unittest discover -s tests -v
python -m py_compile Yihop.py order_core.py order_storage.py auth_core.py
```

測試涵蓋日期／天氣時段、廠商公休、品項隔離、登入、數量格式、兩頁寫入、部分失敗補送與網路在寫入後中斷等情境。GitHub Actions 會自動執行這些檢查。

## 想在面試中分享的部分

最值得談的不是使用了多少框架，而是：**怎樣把門市人員實際會遇到的狀況，變成清楚的資料流程**。我選擇先整合現場本來就使用的 Google Sheets，導入成本較低；但早期做法也因此碰到寫入一致性、快取和多人操作問題，後續才逐步加上送單識別、錯誤回報和回歸測試。

這套專案依然是營運輔助工具，天氣及特殊日期加成屬於規則，不是已用銷售資料驗證準確度的需求預測模型。正式上線前仍需拿實際門市資料、Google Sheet 權限與多人實機操作做整合驗收。
